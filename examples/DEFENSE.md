# DEFENSE · 长度旁路 & 加密推理状态解封：防御向解读

> 本文只做**防御向分析**：解释"解封隐藏推理链"这类做法**利用了哪个 API 行为**、
> 服务方/网关**怎么检测**、**怎么堵**。不提供任何针对真实模型的提取/解封实现，
> 也不指导如何跑通攻击。可运行的部分全部是 `examples/` 里的**纯合成仿真**
> （带噪比较器 + 二分搜索），不碰真实模型、不联网、不处理任何 `signature`。

## 1. 威胁模型：两类要分开看

| | A. 长度旁路（length side-channel） | B. 状态回放解封（signature replay / unseal） |
|---|---|---|
| 目标 | 从"新不透明状态的长度"里读出 1 比特（模型内部某个判定） | 让 provider 把已封存的私有推理链**原文**吐出来 |
| 前提 | 服务方把"工作量"编码进了一个攻击者可测长度的载体 | 服务方允许把**外来 opaque state** 当 `assistant.thinking` 回填并解密 |
| 载体 | opaque_state / usage 字段长度 | `thinking.signature`（AEAD 加密、绑定模型名的 protobuf 封套） |
| 恢复方式 | 成对反转编码 + 差分 + 多次投票 + 二分搜索 | 把 signature 塞回新请求，诱导模型复述其"此前的推理" |
| 合成演示 | `mock_sidechannel_demo.py` | 不提供实现（见 §5） |

两类的共同根因是同一句话:**服务方替攻击者把本该私有的信息，搬到了攻击者能观测/能回填的位置。** 防御也落在同一句话的反面。

## 2. B 类利用的确切 API 行为

参照公开复现物（如 open-open-reasoning）README 自述的流程,它并不"破解密码",而是**借道 provider 自己的解密**:

1. **采集(harvest)**:发一次开启 extended thinking 的普通请求,响应里带回一个 `thinking` 块,内含不透明 `signature`(被封存的推理)。明文推理不离开 provider。
2. **回放(replay/unseal)**:把这个 `signature` 作为 `assistant.thinking` 块塞进一个**新请求**,再让模型复述它"此前的私有推理"。provider 在服务端解密封套,模型把内容surface 出来。

关键点(防御方要盯的):

- signature **从不是顶层字段**,永远藏在某个 `thinking` 内容块里——网关按顶层字段过滤会漏。
- 它**绑定模型名**:回放必须用匹配模型才能过 AEAD 完整性校验。这既是攻击的约束,也是防御的抓手(见 §4)。
- 诱导是**随机的**:同一 signature 偶尔返回拒绝,重试常成功——说明这是模型行为层的诱导,不是确定性解密。

## 3. A 类的机制(用合成数字说清)

`mock_sidechannel_demo.py` 用高斯 oracle(短~N(1200,90)、长~N(4800,180))模拟"新状态长度"。成对反转:请求 A 让真值走长分支、请求 B 走短分支,取差 `D=lenA−lenB`;真则 D>0。多次投票压噪,二分字符集逐位还原。真实跑出:

- 16 位 hex canary `3f0ac1d9b8e27f64` **逐字符还原,exact_match=True**,理论=实测=384 次请求。
- 控制组**移除 opaque state** 后:单判定正确率从 **1.000 掉到 0.497**,还原串完全错——**没有状态,信道就退化成掷硬币**。

这条控制组本身就是最强的防御论据:**信道存活完全依赖真实的 opaque-state 回填**。

## 4. 防御矩阵(来自 `defense_validation.py` 真实输出)

单判定正确率越接近 0.5 越好(=攻击者拿不到比特)。对比"单次判定 @1"与"30 次投票 @30":

| 防御姿势 | 正确率@1 | 正确率@30 | 判定 |
|---|---|---|---|
| 无防御(baseline) | 1.000 | 1.000 | 信道打通 |
| 定长填充 / 长度归一化 | 0.488 | 0.492 | **信道死亡** |
| 随机填充(零均值噪声) | 0.739 | **0.996** | 信道打通(被投票穿透) |
| 分桶·边界没选好 | 1.000 | 1.000 | 信道打通(等于没防) |
| 分桶·粗到吞掉两簇 | 0.511 | 0.505 | **信道死亡**(但字段也废了) |

三个反直觉但真实的结论:

1. **随机噪声不是防御。** @1 被压到 0.739,但攻击者多发几次请求投票,@30 又爬回 0.996——零均值噪声会被平均掉。**加噪只是抬高攻击成本,不改变可达性。**
2. **分桶要做对方向。** 桶边界卡在两簇之间(短→0、长→4000)反而让 Δ 更干净;必须粗到把两簇吞进同一个桶,Δ 才真正→0——可那时这个字段基本没信息量了。
3. **真正干净的做法不在这张表里。** 它不是"把长度变换一下",而是**从源头撤掉 oracle**:不 rehydrate 外来 opaque state,攻击者根本没有可测的长度可读。见 §5。

## 5. 落地缓解清单(按性价比排序)

**根因级(首选):**
- **不 rehydrate 外来 opaque state。** 不接受把客户端传入的 `thinking.signature` / 加密推理块回填进新请求去解密。这一条同时干掉 A 和 B。
- **不对外开启 extended thinking / 不回传 signature。** 没有封存副本,就没有可采集、可回放的目标。

**载体级(纵深防御):**
- **signature 只留在服务端。** 像公开复现物那样按 turn index 引用,响应只暴露布尔 `has_signature`,原始串不发给浏览器——但注意这只挡住"顺手拿",挡不住 BYOK 自带 signature 的路径。
- **长度归一化 / 定长填充**打掉 A 类载体(已验证 @30→0.492)。
- **模型名绑定当防线用。** signature 绑定模型名 → 服务端拒绝跨模型/跨账户回放,让采集来的 signature 无法在别处解封。
- **一次性 / 短时效 signature。** 采集后即失效,回放窗口收紧。
- **usage / 计量字段粗粒度化或加噪**,但记住 §4 结论:加噪只抬成本,分桶要粗到有效,别当银弹。

**检测级:**
- 告警**请求里带入 `assistant.thinking` + 空 thinking 文本 + 非空 signature** 的模式(replay 的指纹)。
- 告警**成对反转式流量**:同一 prompt 家族高频、答案二值化、逐位推进的二分搜索形态。
- 落盘审计 signature 的进出点(采集响应、BYOK 提交、session 回放三处)。

## 6. 现实里往往根本没有攻击面

在正经蒸馏数据里(见 `blackbox_distillation.py` 与幻灯片 §14):teacher 的真实轨迹常常 `reasoning_tokens=0`、`signature=null`——**根本没有被封存的推理可提取**。需要蒸馏数据时,走**只采集可见 input→output** 的黑盒路线即可,合规、可落地、也不需要碰任何隐藏状态。
